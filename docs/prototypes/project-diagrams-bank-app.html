1 · Arquitetura

kind: architecture

As setas sólidas são chamadas, e as tracejadas são “implementa”. O domain não aponta para ninguém. A caixa rosa é o Account do UC-007: está na spec, mas nenhuma classe existe em src/.

Fatos citados

  • pkg:infrastructure.rest, pkg:domain.model … (do packages.map)
  • type:CustomerController, type:CustomerRepository (port), type:Customer (aggregate, @AggregateRoot/spec)
  • impl:CustomerRepositoryJpaAdapter→CustomerRepository (lido do implements)
  • drift:uc:UC-007/aggregate:Account

Regras de desenho

  • Um pacote de adapter com mais de N tipos colapsa em pkg.*
  • Classes de suporte (mapper, config, properties) viram legenda, não caixa
  • Aresta “implementa” só com implements lido no fonte

2 · Blueprint, em caixas

kind: blueprint · style: boxes (opcional)

Contêineres do docker-compose.yml e o sistema externo que a spec nomeia. Cada aresta leva protocolo e o que trafega. O SonarQube aparece cinza e tracejado porque é ferramenta de desenvolvimento, não runtime.

Fatos citados

  • service:app, service:postgres (image), service:kafka, service:keycloak, service:otel-collector, service:sonarqube
  • topic:kyc-verification-requested, topic:kyc-verification-completed (de app.kafka.topics)
  • table:customers … (de CREATE TABLE nas migrations)
  • external:KYC application (linha Trigger do UC-005)

Regras de desenho

  • Serviço com rótulo de ferramenta (lista em extensions.json) fica cinza tracejado
  • Valor de variável nunca aparece; só o nome da chave
  • Sistema externo só entra se uma spec o nomear

2b · Blueprint, só com ícones

kind: blueprint · style: icons (opcional)

Mesmos fatos e as mesmas arestas da versão 2, mas cada peça vira um ícone genérico do seu papel: cilindro para banco, faixas de partição para broker, escudo para identidade, funil para telemetria. Nenhum logo de marca é usado. A cor continua dizendo o papel, e o nome e a imagem ficam embaixo do ícone.

Ícone por papel (não por produto)

  • banco relacional → cilindro · broker → faixas, uma por partição
  • identidade → escudo · telemetria → funil com pulso
  • ferramenta dev → lupa cinza tracejada · externo → nuvem tracejada
  • a app → hexágono em camadas (domain no centro)

Como a skill escolhe

  • Mapa image → icon em extensions.json (ex.: postgres* → database); imagem desconhecida cai em service
  • "style": "brand" | "icons" | "boxes" no view.json; padrão brand (2c), e icons só quando o projeto não quer marca
  • O número de faixas do broker vem de partitions, quando todos os tópicos concordam

2c · Blueprint, com logos reais (padrão)

kind: blueprint · style: brand · padrão

Os mesmos fatos da versão 2, agora com o logo de cada produto, tirado do pacote simple-icons@13.21.0 (traço único, cor oficial da marca). O draw.io não tem logo de Kafka, Keycloak nem OpenTelemetry, e o único PostgreSQL dele é a variante da Azure. Por isso a fonte é o Simple Icons. A peça sem produto conhecido, como o sistema KYC externo e o cliente, continua com ícone genérico.

Fonte e licença por logo

  • Pacote simple-icons@13.21.0: CC0-1.0 no geral, mas a licença de cada ícone vale acima disso
  • Apache Kafka: Apache-2.0, marca da ASF (apache.org/foundation/marks)
  • Keycloak: custom, política de marca da Linux Foundation
  • OpenTelemetry: CC-BY-4.0, exige atribuição
  • PostgreSQL, SonarQube, Spring Boot: sem licença própria no pacote, valem as políticas de marca de cada projeto

Como a skill usaria

  • Ícones copiados em project-diagrams/references/icons/<slug>.svg, com um NOTICE listando fonte e licença
  • Mapa image → slug em extensions.json (postgres* → postgresql)
  • É o estilo padrão do blueprint; sem logo mapeado, a peça cai no ícone genérico da 2b
  • Logo preto vira a cor do texto no tema escuro

3 · Mapa de use cases

kind: use-cases/map

Gatilho à esquerda, caso no meio, o que ele escreve ou lê à direita. O status do caso vem do código: tem classe *UseCase ou não. O UC-004 não tem classe própria porque estende o CreateCustomerUseCase. O backlog aparece apagado embaixo.

Fatos citados

  • uc:UC-001 … uc:UC-007 (título # UC-NNN · …)
  • uc:UC-005/trigger, uc:UC-002/side-effects (linhas da tabela de cabeçalho)
  • type:RecordKycVerdictUseCase → status implementado
  • bl:BL-04 … bl:BL-08 (BACKLOG.md, tabela ativa)

Regras de desenho

  • O verbo da aresta (INSERT, UPDATE, DELETE, read) vem da linha Side effects; sem verbo, a aresta fica sem rótulo
  • Caso sem classe e sem “extends” declarado na spec = rosa, “spec only”

4 · Fluxo de use case

kind: use-cases/UC-006-anonymize-customer

À esquerda, a sequência e, à direita, as decisões, os dois tirados dos blocos mermaid da spec do UC-006. Cada participante ganha um ✓ quando o arquivo existe no código. O diagrama não acrescenta nenhum passo além dos que a spec já tem (rules/spec-diagrams.md).

Fatos citados

  • mermaid:UC-006/00-caso-de-uso.md#sequenceDiagram → participantes e mensagens, na ordem do autonumber
  • mermaid:UC-006/00-caso-de-uso.md#flowchart → decisões e terminais
  • type:AnonymizeCustomerUseCase, type:CustomerRepository, type:Customer → ✓
  • UC-005: uc:UC-005/trigger, uc:UC-005/side-effects, type:KycVerificationCompletedListener

Regras de desenho

  • Participante com nome de tipo e sem arquivo leva ✗ rosa. É drift entre spec e código, e o doctor aponta
  • Alias de prosa (inbound adapter) não é conferido
  • classDiagram e stateDiagram-v2 continuam só na spec: o projeto já os mostra no PR, via GitHub

De 7 specs, só UC-006 e UC-007 têm blocos mermaid. As outras são anteriores à decisão 0143. O caminho de fallback não é exceção: é o caso mais comum hoje.
