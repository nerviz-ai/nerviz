# GitHub Copilot — what it reads from `.claude/`, what needs translation, what does not exist there

This page answers one question: **when someone on GitHub Copilot, rather than Claude Code,
opens a project generated by Nerviz, what do they get?** It is the basis for phase 8 of
`roadmap.md` (multi-agent generated project) and the input to `/claude-code-architect-designer`
when it designs the `AGENTS.md`. It records facts; it decides nothing. The origin of the
problem is `.claude/lessons-learned/lessons-learned-019.md`.

Scope: **the generated project**. The generator (`/init-project`, `project-bootstrap`,
`claude-code-architect-designer`, `arch-adopt`) stays Claude Code only, as decided in
`roadmap.md` § Multi-agent.

Everything here was read from the official documentation on **2026-10-11** (sources at the
end). Copilot changes monthly: anyone using a row of this page in a decision re-checks its
source first. What the documentation does not state is marked **unverified** — and, by this
repository's rule, an unverified guarantee counts as absent.

---

## 1. Vocabulary: Copilot's surfaces

"Copilot" is five runtimes with different readers. A claim about Copilot that does not say
which surface is incomplete.

| Surface | What it is | What it reads from the repository |
|---|---|---|
| **Copilot CLI** | Terminal; the direct counterpart of Claude Code. GA since 2026-02 | More than any other surface: instructions, `AGENTS.md`, `CLAUDE.md`, `.claude/CLAUDE.md`, `.claude/skills/`, hooks from `.claude/settings.json`, `.mcp.json`, agents, skills, plugins |
| **Copilot cloud agent** (formerly "coding agent") | Runs on a GitHub Actions runner from an issue or PR; no user present | `AGENTS.md`, root `CLAUDE.md`, `.github/copilot-instructions.md`, `.github/instructions/`, `.github/agents/`, skills, **only** `.github/hooks/*.json`; MCP only through the repository settings UI |
| **VS Code** (chat, agent mode) | Extension; currently two harnesses, "Local agent" (being removed) and "Agent Host" | Instructions, `AGENTS.md` (root; nested is experimental), `CLAUDE.md`, skills from `.claude/skills/` and `~/.claude/skills/`, agents, hooks (`.github/hooks/`, `.claude/settings.json` via `chat.useClaudeHooks`), `.vscode/mcp.json` and `.mcp.json` |
| **Code review** | Automatic PR review | `.github/copilot-instructions.md`, `AGENTS.md`, `CLAUDE.md`, `.github/instructions/` with `excludeAgent`, skills |
| **Chat on GitHub.com, JetBrains, Visual Studio, Xcode, Eclipse** | Chat on the site and in the IDEs | `.github/copilot-instructions.md`; `AGENTS.md` only through the cloud agent; agents and skills in preview |

For Nerviz, the CLI is the surface that matters most: it is the only Copilot in which
`ArchHook` runs at all.

## 2. How each piece works in Copilot

### 2.1 Always-on instructions

- **`.github/copilot-instructions.md`** — one file, no frontmatter, read by every surface.
  Included in every request made in the context of the repository. No documented size limit;
  the official guidance is "up to about 1,000 lines" and "very long instruction files may
  result in some instructions being overlooked".
- **`AGENTS.md`** — root and **nested**: "the nearest `AGENTS.md` file in the directory tree
  will take precedence". Read by the cloud agent, code review, VS Code chat (root by default;
  nested behind `chat.useNestedAgentsMdFiles`, experimental, which only **lists** the files for
  the agent to open) and the CLI. **Not** read by GitHub.com chat or Visual Studio.
- **`CLAUDE.md` and `GEMINI.md`** — the cloud agent accepts "a single `CLAUDE.md` or
  `GEMINI.md` file stored in the root of the repository" as an alternative to `AGENTS.md`. The
  CLI reads `CLAUDE.md` **and** `.claude/CLAUDE.md`. VS Code reads `CLAUDE.md`,
  `.claude/CLAUDE.md`, `~/.claude/CLAUDE.md` and `CLAUDE.local.md` (`chat.useClaudeMdFile`,
  default `true`). **No surface documents reading a module-level (nested) `CLAUDE.md`**: the
  nesting Copilot knows is `AGENTS.md`'s.
- **`@path` imports** — only the **CLI** expands them, and only inside
  `.github/copilot-instructions.md`, `AGENTS.md` and `CLAUDE.md`; recursive; relative path
  inside the repository; "not expanded in `GEMINI.md` or `*.instructions.md` files". Cloud
  agent and VS Code: nothing documented — in VS Code a Markdown link loads its target only with
  `chat.includeReferencedInstructions`, default `false`.
- **Merge and precedence** — "all sets of relevant instructions are provided to Copilot":
  personal > repository > organization; within the repository, path-specific > repo-wide >
  agent. The CLI "combines" them, removes identical duplicates and "does not define a general
  precedence order". The official guidance on both sides is the same: do not write conflicting
  instructions.

### 2.2 Path-scoped norms — `.github/instructions/*.instructions.md`

The counterpart of `paths` in `rules/`. Frontmatter: `applyTo` (comma-separated globs in a
**string**, not a YAML list: `"**/*.java,**/*.kt"`) and `excludeAgent` (`"code-review"` or
`"cloud-agent"`). VS Code also accepts `name` and `description`. The whole file is attached
when the glob matches a file the agent reads, creates or edits; `applyTo: "**"` always
applies. On GitHub.com only the cloud agent and code review honor it; in the IDEs, chat too;
the CLI too. **`.claude/rules/` is read by no surface.**

### 2.3 Skills — `SKILL.md`

Same specification (agentskills.io). Project directories: `.github/skills/`,
**`.claude/skills/`**, `.agents/skills/` — every surface. Personal: `~/.copilot/skills/`,
`~/.agents/skills/`; `~/.claude/skills/` only in the VS Code documentation.

Frontmatter named by the GitHub documentation: `name` (required, kebab, equal to the
directory), `description` (required), `license`, `allowed-tools` (pre-approves tools: "without
asking for confirmation each time"). VS Code also documents `disable-model-invocation`,
`user-invocable`, `argument-hint` and `context: fork` (experimental). Limits: `name` ≤ 64,
`description` ≤ 1024; "names with invalid characters cause the skill to silently fail to
load". Behavior on unknown frontmatter: **undocumented** — in Claude Code it is silence too,
which is why `schema` exists.

Invocation: the model decides from the `description` ("does not guarantee that it invokes"),
or the user types `/name text`. The text after the name is **appended to the prompt**; there is
no `$ARGUMENTS`. There is no `` !`command` `` injection: the body arrives verbatim.

### 2.4 Agents — `.github/agents/*.agent.md`

Official frontmatter: `name`, `description` (required), `tools` (list or string; omitted or
`["*"]` = all; `[]` = none; "unrecognized names are ignored"), `model` (IDEs only; GitHub.com
ignores it), `target` (`vscode` | `github-copilot`), `disable-model-invocation`,
`user-invocable` (`false` = subagent only), `mcp-servers` (GitHub.com), `metadata`. VS Code adds
`agents` (subagent allow-list), `handoffs`, `hooks`. The CLI adds
`include-custom-instructions: true` — **by default a subagent does not receive the
repository's instructions**. Body ≤ 30,000 characters. For GitHub.com the file must be on the
default branch. The old `.github/chatmodes/*.chatmode.md` files were renamed to this.

Directories: `.github/agents/` (project), `~/.copilot/agents/` (user), `/agents/` in the
organization's `.github` or `.github-private` repository. **`.claude/agents/` does not appear
in the CLI or cloud agent documentation** (a VS Code note mentions reading `.claude/agents` in
Claude format — unverified outside VS Code).

Model-invoked delegation: exists in the CLI ("may choose to use one of your custom agents … in
a subagent with its own context window") and in VS Code (`runSubagent`); **not** on GitHub.com.
The CLI ships built-in subagents (Explore, Task, General-purpose, Code-review, Plan), `/fleet`
for parallelism, `/plan` and plugins (`copilot plugin install`, which reads
`.claude-plugin/plugin.json`).

### 2.5 Hooks

"Hooks are supported in two Copilot surfaces: Copilot CLI and Copilot cloud agent." VS Code
has its own hooks (`chat.useHooks`) and reads the Claude format with `chat.useClaudeHooks`.

- **Where**: `.github/hooks/*.json` (`{"version":1,"hooks":{…}}`). The cloud agent reads
  **only** that, and only from the default branch — it "does not load `settings.json`". The CLI
  also reads `.github/copilot/settings.json`, `~/.copilot/hooks/`, machine policy in
  `/etc/github-copilot/policy.d/` and **"cross-tool `.claude/settings.json` and
  `.claude/settings.local.json` files in the repository"**.
- **Events (camelCase)**: `sessionStart`, `sessionEnd`, `userPromptSubmitted`,
  `userPromptTransformed`, `preToolUse`, `postToolUse`, `postToolUseFailure`,
  `permissionRequest`, `agentStop`, `subagentStart`, `subagentStop`, `preCompact`,
  `notification`, `errorOccurred`. In the cloud agent, `notification` never fires,
  `permissionRequest` is a no-op and `preCompact` fires only with `trigger: "auto"`.
- **Two payload formats, selected by the event name.** In camelCase: `sessionId`, `timestamp`,
  `cwd`, `toolName`, `toolArgs` (JSON string). In **PascalCase** (`PreToolUse`, "as used in
  Claude Code plugins"): `hook_event_name`, `session_id`, `cwd`, `tool_name`, `tool_input`,
  with **Claude's tool names** (`Bash`, `Read`, `Write`, `Edit`, `Grep`, `Glob`,
  `AskUserQuestion`, `Agent`; `Task` accepted in matchers) and Claude's matcher semantics.
  `tool_input` is typed `unknown`, "tool arguments, parsed from a JSON string when possible" —
  **its inner shape (`command`, `file_path`, `content`) is undocumented**. `SubagentStart` and
  `StopFailure` **have no PascalCase alias**.
- **Blocking**: stdout with `{"permissionDecision":"deny","permissionDecisionReason":"…"}`
  (flat, not nested in `hookSpecificOutput` — Claude Code's nested form is undocumented);
  `exit 2` always denies, "even if the hook's stdout JSON reports allow"; any non-zero exit
  denies (fail-closed); a timeout lets the call through (fail-open). In the cloud agent, `ask`
  becomes `deny`. `agentStop`/`subagentStop` accept `decision: "block"`.
- **Context**: `additionalContext` on `sessionStart`, `subagentStart` ("prepended to the
  subagent's first user message"), `postToolUse` and `notification`.
- **Declaration**: `type` (`command` by default; `http`; `prompt` CLI only),
  `bash`/`powershell`/`command`, `exec` + `args` (CLI only, no shell), `cwd`, `env`,
  `timeoutSec`, `matcher` (regex, `^(?:…)$`). `$CLAUDE_PROJECT_DIR`: **undocumented**.

### 2.6 MCP

- **CLI**: `~/.copilot/mcp-config.json`; in the repository, **`.mcp.json`** (searched from the
  cwd up to the root; wins) and `.github/mcp.json`; accepts the `mcpServers` wrapper or the bare
  map; loaded only after the user confirms folder trust. **Does not read `.vscode/mcp.json`**
  (`servers` key). `${VAR}` interpolation in `env`/`headers`: **undocumented** — the official
  text writes values literally.
- **VS Code**: `.vscode/mcp.json` (`servers`, `inputs` with `${input:id}`); also reads `.mcp.json`.
- **Cloud agent**: only through the UI (Settings → Copilot → MCP servers), JSON `mcpServers`,
  secrets in Actions secrets prefixed `COPILOT_MCP_*`, referenced as `${VAR:-default}`. No file
  in the repository.

### 2.7 Permissions

- **CLI**: `--allow-tool`/`--deny-tool` with the grammar `shell(git:*)`, `write(README.md)`,
  `url(https://*.github.com)`; `--allow-all-tools`, `--yolo`; `/permissions`; saved approvals in
  `~/.copilot/permissions-config.json`. "Deny rules always take precedence over allow rules,
  even when `--allow-all` is set." A `permissions.deny` key in a repository file:
  **undocumented**.
- **Enterprise**: `managed-settings.json` with `permissions.deny|ask|allow` and rules
  `Bash(...)`/`Shell(...)`, `Read(...)`, `Edit(...)`/`Write(...)`, `Domain(...)` — the same
  grammar as Claude Code's `settings.json` — honored by the CLI, VS Code, the app and the cloud
  agent.
- **VS Code**: `chat.tools.terminal.autoApprove` and related settings; `false` only forces a
  prompt; blocking requires a `PreToolUse` hook returning `deny`.
- **Cloud agent**: firewall with an allowlist (includes `repo1.maven.org`,
  `services.gradle.org`, `plugins.gradle.org`, Docker Hub); applies only to Bash processes, not
  to MCP servers nor to `copilot-setup-steps.yml`.

### 2.8 Cloud agent environment and transcripts

- `.github/workflows/copilot-setup-steps.yml`: one job named `copilot-setup-steps`; only
  `steps`, `permissions`, `runs-on`, `services`, `snapshot`, `timeout-minutes` (≤ 59); Ubuntu
  x64 or Windows; default branch. This is where the JDK is installed and `./mvnw` warmed up.
- Transcript: CLI in `~/.copilot/session-state/<id>/events.jsonl` (its own format; token counts
  **unverified**). Cloud agent: UI only. Hooks receive `transcriptPath` on `agentStop`,
  `subagentStop`, `preCompact`.

## 8. Facts that bind the `AGENTS.md` design

These are not decisions. They are what the documentation pins down, so that
`/claude-code-architect-designer` does not rediscover them.

1. **Claude Code, the Copilot CLI, the cloud agent and VS Code all read the root `CLAUDE.md`.**
   Only Claude Code and the Copilot CLI expand an `@AGENTS.md` inside it. A `CLAUDE.md` that
   only imports `AGENTS.md` leaves the cloud agent with two files and a dead import.
2. **Claude Code reads `AGENTS.md` natively since v2.1.277, but only when there is no
   `CLAUDE.md` on the path** (`claude-help.md` § AGENTS.md). With both, it reads only
   `CLAUDE.md`. The officially preferred way to share is `@AGENTS.md` inside `CLAUDE.md`, not a
   symlink.
3. **The only nesting that crosses both runtimes is nested `AGENTS.md`, and in Claude Code
   only through an import.** A module `AGENTS.md` alone is **not** read by Claude Code while the
   root has a `CLAUDE.md` — the documentation leaves the case open; Claude Code 2.1.296 did not
   load it on a Read. A module `CLAUDE.md` holding only `@AGENTS.md` loads it on a Read, Edit or
   Write under the module, inside a subagent too (reproduced on 2026-10-11). Copilot never reads
   a nested `CLAUDE.md`. Hence the shape of decision 0139: the module `AGENTS.md` is the owner,
   and the `CLAUDE.md` next to it only imports it.
4. **Copilot reads `.claude/skills/` as-is**, but no `disable-model-invocation` is guaranteed
   outside VS Code. The 14 manual skills become, under Copilot, candidates for automatic
   invocation — including `arch-adopt`, which rewrites `.claude/`.
5. **`.claude/rules/` does not exist for Copilot.** Until the derivation of step 3, the only
   path is a citation by path inside `AGENTS.md`.
6. **Hooks in `.claude/settings.json` run in the Copilot CLI, and only there.** Whatever
   `AGENTS.md` promises about `guard` must tell the CLI apart from the cloud agent.
7. **The cloud agent has no user.** Any flow that goes through `AskUserQuestion` or through two
   confirmations (`git-publish`) does not finish there.
8. **Who adds up and who picks.** The Copilot CLI and VS Code add every instruction file up,
   with no precedence order. The cloud agent reads "`AGENTS.md`, `CLAUDE.md` or `GEMINI.md`";
   which one wins when the root has two is not documented. VS Code does not expand `@path` —
   Markdown links only, and only with `chat.includeReferencedInstructions` (default `false`).
   Chat on GitHub.com, Visual Studio, JetBrains, Xcode and Eclipse reads only
   `.github/copilot-instructions.md`.
