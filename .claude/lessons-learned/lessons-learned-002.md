# Lessons learned — UC-000, bootstrap of `demo-application`

Document intended for the **meta-repo** (the project generator, blueprint
`clean-architecture-single-module`), not for the generated project.

Record of the points where `project-initializer` had to **infer**, **fix**, or
**contradict** the generated material — templates, blueprint, `pom.xml.example`,
`ci.yml.example`, cross-skill references — to get `demo-application` bootstrapped with a
green `./mvnw clean verify`. No business code exists yet; every gap here is in the
scaffolding itself, before any use case is implemented.

Execution context: Spring Boot 4.1.1, Java 21 (forced — Initializr's default is 17),
Maven, Testcontainers with `postgres:latest`. Target directory:
`~/Documents/GitHub/demo-application`, groupId `com.<user>`.

## 1. `logback.xml` is written where logback can't find it

**Evidence.** Step 4.9 of the bootstrap procedure and `.claude/rules/logging.md` §
`logback.xml` both mandate the file at `<project>/logback.xml`, "root, next to the root
`pom.xml`". Logback only resolves its config from the **classpath root**. Confirmed
twice after build: `target/classes/` contains `application.yml` and compiled classes,
but no `logback.xml` — and the test run's own log lines use Boot's default pattern, no
`traceId` field present:

```
2026-09-09T22:38:11.443+01:00  INFO 82553 --- [demo-application] [main] com.zaxxer.hikari.HikariDataSource : ...
```

**Cost.** Silent — the build is green, nothing errors, the file is simply never loaded.
`logging.md`'s entire per-line contract (pattern, level semantics, sensitive-data
exclusion) is enforced by nothing in every project this blueprint generates.

**Meta-repo fix.** Move the write target to `src/main/resources/logback-spring.xml`
(the Spring-Boot-aware variant, so profile-based overrides still work) in both the
bootstrap step and `logging.md` — they're the two owners and must change together, per
invariant 2.

## 5. Initializr call defaults to Java 17

**Evidence.** Step 3's `curl` passes no `javaVersion`. First response under Boot 4.1.1
came back `<java.version>17</java.version>`. The skill's own precondition is JDK 21+,
and `dependency-catalog.md` reasons explicitly about "the target is 21" for `uuid-v7`.
Had to regenerate with `-d javaVersion=21`.

**Cost.** Low to fix once noticed, but a silent contradiction between the precondition
gate and the actual generated `pom.xml` — a project could bootstrap successfully on 17
and only fail later against rules written assuming 21.

**Meta-repo fix.** Step 3's `curl` command adds `-d javaVersion=21` (or reads it from
the blueprint if this ever needs to vary).

---

## 7. Generated header comment breaks the autonomy check it's supposed to survive

**Evidence.** Step 5's suggested file header reads
`# Generated by /init-project from blueprints/<id>.yaml`. Step 8 mandates
`grep -rn "blueprints/" .claude/ CLAUDE.md */CLAUDE.md` return nothing, to guarantee
invariant 9 (self-contained project, no reference back to the meta-repo). The header
template fails its own generator's verification.

**Cost.** Would have failed step 8 on every single bootstrap, forcing a manual reword
each time — caught this run only because the step was executed carefully.

**Meta-repo fix.** Reword the header to name the blueprint without the `blueprints/`
path segment, e.g. `# Generated by /init-project — blueprint: <id>`.

---

## 2. `ci.yml.example`'s IT check is red from commit zero

**Evidence.** Per decision 0011, the workflow has an "integration tests actually ran"
step. As written it fails when no failsafe report exists — but a bootstrapped project
has zero business code and therefore zero `*IT.java`, exactly as step 8 describes the
expected state. CI would be red before any feature work starts.

**Cost.** Medium — first thing a new contributor sees is a failing pipeline, for a
reason unrelated to their change.

**Meta-repo fix.** Key the check off `*IT.java` source presence: no IT sources → pass
with an informational note; sources present but no report, or `Tests run: 0` → fail.
Preserves the anti-degradation intent from decision 0011 while not punishing an empty
scaffold.

## 3. `pom.parent.xml.example`'s JaCoCo comment is wrong

**Evidence.** The template comment states "No `<version>`: the Spring Boot parent pins
it" for both failsafe and JaCoCo. True for failsafe. False for JaCoCo —
`spring-boot-starter-parent:4.1.1` contains zero `jacoco` references (`grep -c jacoco`
on the parent POM returns 0). Build logs a warning and resolves JaCoCo `0.8.15`
non-reproducibly, i.e. whatever's newest at build time.

**Cost.** Low now, but reproducibility risk grows over time as new JaCoCo releases ship.

**Meta-repo fix.** Add an explicit `<jacoco.version>0.8.15</jacoco.version>` property and
correct the comment to state only failsafe is parent-managed.

---

## 6. `postgres:latest` floats in the generated Testcontainers config

**Evidence.** The Initializr's own `TestcontainersConfiguration` pins no tag. Observed
engine: Postgres 18.6. One of five `./mvnw clean verify` runs failed at container start
(transient, 1.4s in). Not the bootstrap's fault to fix directly — pinning the engine
version is `persistence-architect`'s call, and step 8 forbids the bootstrap writing into
`src/test/**` — but worth tracking as a recurring flake source across every generated
project until `persistence-architect` addresses it.

**Cost.** Medium, intermittent — the kind of flake that erodes trust in `verify` over
many runs.

**Meta-repo fix.** `persistence-architect`'s container setup should pin a specific
Postgres tag (e.g. `postgres:18.6`) instead of `latest`.

---

## 4. Step 6.7's correction table is incomplete

**Evidence.** The step names 3 skills (`rest-api-architect`, `test-architect`,
`persistence-architect`) needing the "no blueprint in generated project" correction for
references to "the active blueprint's `packages.map`". In fact 6 skills carry the
phrase — the same three plus `domain-modeling`, `use-case-design`, and the
`use-case-spec.md.example` template (3 lines). Applied the same rewrite to all six this
run; the step itself still only lists three.

**Cost.** Low this run (caught by reading broadly), but the step under-specifies its own
scope — a future executor following it literally leaves 3 stale references behind.

**Meta-repo fix.** Update step 6.7's correction table to list all six locations, or
better, replace the fixed list with a `grep -rl "active blueprint's \`packages.map\`"`
executed at bootstrap time so the set is never stale.

---

## 8. `demo-application` has no git repo yet

**Evidence.** `ArchHook.java doctor` flags that the `tests` Stop hook won't run until
there's a first commit. Left uninitialized on this run — user chose not to init now.

**Cost.** None yet; purely a follow-up item for whoever picks the project back up.

**Meta-repo fix.** None needed in the meta-repo. Consider whether step 8's final report
should surface this more prominently (it currently doesn't mention git state at all)
so it isn't missed on a non-interactive/unattended run.

---

## Underlying pattern

Unlike lessons-learned-001 (where the gaps surfaced only once business code existed),
every gap here was found **before a single domain class was written** — in the scaffold
itself. Three of eight (1, 5, 7) are the bootstrap contradicting its own stated
preconditions or its own verification step. The same remedy proposed in 001 applies
here with no modification: **a reference project generated in CI**, where the full
`verify` runs, the autonomy `grep` runs, and `logback.xml` is asserted to be on the
classpath, would have caught 1, 2, 5, and 7 with no human execution needed.

## Appendix: what went well

- **Blueprint validation (step 2) caught nothing wrong** — `clean-architecture-single-module.yaml`
  passed all 6 checks cleanly, including the `templates.*` resolution and the single
  `contains_main` check.
- **The boundary hook worked correctly** on the first try in both directions (forbidden
  import blocked, permitted import allowed) — derived from `dependency_rules.forbidden`
  with no ambiguity, despite the blueprint being single-module.
- **Lombok enforcement worked as specified** — `@Setter` on a generated class was
  blocked with the exact configured message.
- **The self-contained check (invariant 9) passed** after the header fix — no dead
  `blueprints/` reference remained in the generated project.
